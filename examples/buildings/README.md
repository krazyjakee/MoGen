# Building examples

`.mog` files here are hand-authored MoGen source and build like any other
example.

## `gatehouse.pascal.json`

The one file here that is **not** MoGen source. It is a
[pascalorg/editor](https://github.com/pascalorg/editor) scene, kept as the
importer's main test case:

```sh
mogen import examples/buildings/gatehouse.pascal.json --out /tmp/gatehouse.mog
mogen build /tmp/gatehouse.mog --out /tmp/gatehouse.glb
```

A T-plan house — a 14×8 m main block with a 6×5 m wing — over two storeys plus
a roof level, cross-gabled so the wing carries its own ridge. 26 walls, doors
and windows on every external wall, slabs and ceilings per storey, and twelve
furniture items that import as POI markers rather than meshes.

Its openings come back as `use "door_simple"` / `use "window_simple"` rather
than as bare holes, so the doors and windows are real geometry you can re-aim
by changing one module name.

### It is generated, not hand-written

`crates/mogen-pascal/tests/fixtures/make_gatehouse.py` emits it:

```sh
python3 crates/mogen-pascal/tests/fixtures/make_gatehouse.py
```

Keeping the generator rather than only its output means the awkward parts below
are declared on purpose and can be adjusted, instead of being mystery bytes in
a fixture. Edit the script, re-run it, run `cargo test -p mogen-pascal`.

### What it is for

Small fixtures only ever contain shapes we already thought of. Every importer
bug so far has lived in the gap between *a scene* and *a building*, so this file
carries four things a tidy fixture would not:

- **A `site` polygon in the wrapped form**, `{type, points}` rather than a bare
  ring. That shape only appears in scenes taken from the running app — their
  file exporter flattens it — and one such node used to abort the whole load.
- **A `roof` container with a non-zero transform**, its segments positioned
  relative to it. Read only the segments and the roof lands at the world origin;
  the editor's own demo scene keeps every container at the origin, so this was
  invisible until a real roof floated off the walls. Its Y offset is negative,
  which taken literally drops the main ridge *below* the storey it covers —
  `arch::roof` lifts the eave back onto the wall tops and reports it, because
  the alternative is a row of walls poking out through the slopes with no
  diagnostic to say so.
- **Sparse level ordinals** (0, 3, 5) with no `height` field. Their level
  numbers skip by design and elevation comes from the prefix sum of the levels
  below, not from the ordinal.
- **Four deliberately malformed shapes**, below.

### It does not import cleanly, on purpose

The imported `.mog` header reports seven items needing attention. Six come from
four planted defects: a self-intersecting ring, a hole hanging outside its slab,
a zero-length wall, and a wall bowed tighter than its own half-thickness. Their
editor tolerates all four. We drop the shape and say so, because emitting one
means a hole in the mesh. The seventh is the sunken roof container above.

That last one is why the fixture earns its keep. It was accepted or rejected
*depending on how far the building sat from the origin* — its footprint doubles
back along itself rather than properly crossing, so `ring_is_simple` only caught
it when f32 noise happened to tilt the two collinear edges. Everywhere else it
became a capless tube with no diagnostic. Fixed in
`arch/plan.rs::segments_overlap_collinearly`.

Keeping a file that *doesn't* import perfectly is the point. If it ever reports
zero problems, the interesting possibility is not that the fixture improved — it
is a constant — but that something stopped refusing geometry it should refuse.
`crates/mogen-pascal/tests/real_project.rs` asserts exactly that.

### Provenance

Ours. Designed for this repository and generated by the script above, so it
carries no third-party licence.

It follows pascalorg/editor's *format*, which is MIT-licensed
(`Copyright (c) 2026 Pascal Group Inc.`) and documented in
`crates/mogen-pascal/src/schema.rs`. Note that their MIT licence covers their
editor's code — projects users create with it stay the property of those users,
and their terms grant Pascal an operational licence rather than a redistribution
one. That is why this fixture is authored rather than borrowed from the
community gallery.
